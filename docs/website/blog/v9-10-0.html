What's in 9.10.0

Five months since the last post. I moved house and the day job got loud. That's the whole explanation, and it's a more honest one than "we've been heads-down building."

This release is mostly a list of things that didn't work the way the documentation said they did. Not many new features. If you're running 9.9.0, several of these matter.

Things that didn't work the way the docs said

Config push could reboot a router on a push that succeeded. The device-side revert was a RouterOS scheduler on a 90-second timer. It never checked whether the device was reachable — it just fired, and the only thing stopping it was TOD racing back to delete it first. Because the timer was anchored to the device's last boot rather than to when it was installed, TOD lost that race about 72% of the time, and losing it meant /system backup load: config reverted, device rebooted, on a change that had worked fine.

That's gone. Config restores and template pushes now run inside a RouterOS safe-mode session. The change is applied inside the session, TOD dials a new connection to check the device still answers, and only then commits. If the device doesn't answer — or if TOD crashes, or loses its network mid-push — the session drops and RouterOS reverts every change made in it, by itself, without rebooting. Verified on real hardware; device uptime ran continuously through every test.

One limit worth knowing: safe mode's undo buffer holds 100 actions, and past that RouterOS silently keeps the changes while still reporting it's in safe mode. So a push over that size is now refused rather than applied without a safety net. Split a large template into stages.

This does not cover direct edits in the config editor. Those still apply immediately with no rollback, and the toggle that used to imply otherwise has been relabelled.

The WinBox idle timeout had never fired. Not once. It looked for a field name that this version of xpra doesn't emit, so it matched nothing in every session state and silently gave up. An abandoned session therefore held one of ten concurrency slots — and an authenticated connection to your router — for the full two-hour maximum lifetime. Leaks one through nine were invisible; the tenth handed everyone a 503.

Disconnects are now detected directly from the client count, which is present whether or not a client is attached, and a disconnected session enters a 30-second grace period before teardown. Sweeps run every 30 seconds, so a slot comes back in about a minute instead of two hours, and a reconnect inside the grace window cancels it.

Separately, a crashed session left roughly 300MB of live processes running while the worker reported the slot free. The worker now reaps its own orphans. Verified against real hardware.

Device onboarding only checked that a port was open. A TCP connect, nothing more. A RouterOS device with api-ssl enabled and no certificate installed would onboard green and then fail every single poll afterwards, because there's no cipher overlap and the failure happens during negotiation, not connection. Onboarding now completes a real protocol handshake — TCP, TLS, then an actual API login — and when it fails it tells you why, in those terms, instead of "unreachable". There's also a test-connection endpoint now so you can re-run the same probe against a device you've already added.

The README said the free tier was 1,000 devices. The licence says 250. The licence has said 250 since March, and the licence is the number that counts. The README was simply never updated, and it's been wrong for five months. Fixed, and there's now a test that fails the build if the licence, the code and the documentation ever disagree again.

Security

A validation error could echo your credentials back to you. Mistype a field while creating a credential profile and the HTTP 422 response contained the entire submitted body — RouterOS password, SNMP v3 passphrases, SSH key passphrase, whatever you'd sent. Pydantic includes the raw pre-validation input in its error entries and FastAPI serialised it verbatim; SecretStr doesn't help, because the masking applies to the parsed value and this is the raw one. It wasn't new, and it wasn't limited to one field.

The 422 handler now strips the submitted input from every error entry and keeps only which field failed and why. If you've been creating credential profiles through the API and logging responses, your logs are worth a look.

Bugs that were live in 9.9.0

  • The Add Device form threw a ReferenceError on several paths — a state variable had been deleted in a lint cleanup while two call sites were left behind.
  • Emergency rollback threw on both outcomes. Success and failure each hit a TypeError instead of telling you what happened.
  • The firewall panel's row menu threw on open — two icons used without being imported.
  • The adoption wizard reported every freshly adopted device as unreachable. It waited five seconds and read a status the poller hadn't written yet; the poller's interval is 60 seconds.
  • The adoption wizard's port selector did nothing at all. Picking 8728 or 8729 changed nothing about the request that got sent.

Under the hood

CI's TypeScript check was passing while checking zero files. The config is solution-style, so a bare tsc --noEmit resolves no inputs and exits 0 instantly. The real build reported 60 errors across 25 files — including the Add Device bug above, which is how it shipped in the first place. The check now follows the project references, and all 60 are fixed rather than silenced.

Container vulnerability scans were running but couldn't fail a build. They can now, on CRITICAL and HIGH.

The WinBox worker wasn't being linted in CI at all — only the poller was. It is now, and it has a test suite for session lifecycle, though wiring that suite into CI is still outstanding.

Postgres and Redis had no restart policy. After a host reboot, Docker starts only containers that carry one, so those two stayed down while the API and poller crash-looped against them until somebody logged in and noticed. depends_on doesn't help here; it doesn't apply to daemon-driven restarts. Fixed.

The poller's health check always said healthy. It returned {"status":"ok"} unconditionally, so a poller that had lost NATS and was discarding every sample it collected still passed. It now probes each dependency and returns a 503 naming the one that failed. The API had no health check wired up at all, despite already having a readiness probe that checks PostgreSQL, Redis and NATS.

Documentation

A pass over the website and docs to bring the claims into line with the code. The config push description was wrong in the ways above. "Orphaned containers" was the wrong explanation for the WinBox leak — there are no per-session containers. Several pages described the product as open source when the licence is BSL 1.1, which is source-available; it converts to Apache 2.0 in March 2030. And the structured data was advertising the product as free with no mention of the commercial licence.

None of that changed what the software does. It changed what the site claims it does, which had drifted further than I'd like.
